---
name: retro
description: Retrospective — turn this session's friction into durable repo improvements (the compounding loop)
argument-hint: "[optional focus area, e.g. 'particle animation']"
---

You just finished a task. Run a **compounding-loop retrospective** so the next
task in this repo is closer to one-shot. Be honest and concrete, and prefer
patching the repo over re-explaining things in chat.

Work through these steps:

1. **Diagnose the friction.** Look back over THIS session and name the specific
   things that cost tokens or caused back-and-forth: wrong guesses, missing
   context, repeated verification, commands you had to discover, knowledge you
   re-derived from scratch, edits that matched the wrong file. Quote concrete
   moments instead of generalizing. If `{{args}}` is non-empty, focus the
   retrospective there.

2. **Map each friction point to a durable artifact.** For each one, name what
   would have prevented it:
    - a line in `AGENTS.md` (sparingly — only broadly useful, stable facts,
      since it auto-loads into every session);
    - a knowledge doc under `docs/` for subsystem detail;
    - a `Makefile` target (`make check`, `make gate`, `make fix`, `make fmt`);
    - a Jest test or ESLint/Prettier/Stylelint gate;
    - a new or updated `.agents/skills/<name>/SKILL.md` (`.claude/commands/` is
      generated by `tools/sync_commands.py`).

3. **Check what already exists first.** Read `AGENTS.md`, `Makefile`,
   `.pre-commit-config.yaml`, lint configs, `docs/`, and `.agents/skills/`
   before adding anything, so you patch real gaps instead of duplicating. Repo
   knowledge belongs in version-controlled files rather than chat or memory.

4. **Implement the safe, high-leverage fixes now.** Knowledge capture, scoped
   commands, deduplication, and tests/gates are usually safe to land directly.
   Promote standards up the ratchet: prose → checklist → lint/type rule →
   CI-blocking check — a gate makes the prose redundant, so shrink the prose
   when you add one.

5. **Ask before anything heavy or hard to reverse** — new dependencies, tool
   installs, CI workflow changes under `.github/`, file moves, anything
   outward-facing. Present the trade-off and let the user choose.

6. **Verify and report.** Run `make check` (and `npx jest` when tests are
   relevant), keep lint and tests green, and summarize what you changed and how
   it pays off next time. Commit only when explicitly asked.

7. **Distill the session into a skill delta (ACE step).** Ask: "what did this
   session teach about _how_ to do X?" If the answer generalizes beyond this
   task, edit the existing `.agents/skills/*/SKILL.md` or `AGENTS.md` it
   belongs to rather than spawning a near-duplicate skill. Every line in an
   auto-loaded file is paid for in every session, so a line earns its place
   only if it is a repo/environment fact a capable model can't infer, a user
   preference, or cheaper than rediscovery. Write it as the fact or goal
   ("assert gallery tests against synthetic fixture `p99`"), not a new
   prohibition or an incident story (dates and PR numbers belong in commit
   messages and docs). When the section you touch already covers the point,
   merge or replace instead of appending. Run `python3 tools/sync_commands.py`
   and `make sync-check` after any skill edit.

Guiding test: _a correction given today should be impossible to need next
month_ — because it now lives in the repo, not in this conversation.
